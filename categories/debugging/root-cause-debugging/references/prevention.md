# 防复发：保护具体行为，而非增加规则数量

## 1. 记录可执行的正确性要求

每条要求写明：对象/身份范围、前置条件、允许行为、禁止结果、业务来源、执行位置和测试入口。
先复用已有要求，不为每个 Bug 重复创建一个 invariant ID。没有业务依据时，不发明唯一性或不可变规则。

教学例：“归档操作成功提交后，档案状态与该次封存回执一致；失败则二者不部分提交。”
这是示例产品的原子性约定，不是对任何具体档案系统或法律合规要求的断言。
“一个逻辑文件一个身份”还需区分租户、版本、逻辑引用、物理对象、重传与重复件，不能直接加全局 UNIQUE。

## 2. 在有能力保护该要求的边界实现

| 错误类型 | 优先检查的保护机制 | 验证重点 |
| --- | --- | --- |
| 单条数据取值/引用错误 | 数据库约束、领域校验、边界契约 | 合法历史数据、迁移、错误语义 |
| 多步持久化部分成功 | 合适的事务边界及失败恢复 | 任一步失败、回滚、重试和读取一致性 |
| 并发检查后写入 | 原子操作、锁或版本比较等现有机制 | 受控竞争、隔离级别、丢失更新 |
| 跨系统操作不一致 | 持久化意图、幂等、恢复/补偿等现有设计 | 重复/乱序、消息丢失、崩溃窗口 |
| 接口或业务语义分歧 | 共享契约、兼容性测试、边界转换 | 老调用方、空值与错误、版本 |
| 容量/超时/资源错误 | 有界队列、预算、取消与回收等合适约束 | 边界负载、超限反馈、资源释放 |

这是排查选项，不是自动选型指令。先检验仓库已有设计，禁止因一个 Bug 引入整套基础设施。
应用层先查后写不能单凭顺序代码证明并发安全；相应保证需要在实际竞争模型下验证。
数据库约束不能代替全部跨记录、跨系统与时序要求；事务的实际边界也必须核对。

## 3. 用不同测试回答不同问题

历史回归测试：这次真实失败条件是否被覆盖？必须验证修前失败，不是仅在修后新增一个绿色测试。
相邻行为测试：修复是否破坏原来正确的合法输入、状态或接口？
集成测试：真正出现缺陷的边界是否经过真实执行，而不是只 mock 出预期结果？
性质/状态模型测试：输入组合或事件序列很大时，用已有测试能力扩大覆盖，而不是新增无关平台。
故障注入/关键修复撤销：测试是否真的能发现目标机制？只在隔离副本进行。
并发测试：固定可控调度或明确试验规模；“运行一次未失败”不能证明不存在竞争。

## 4. 历史数据与发布

阻止新错误不等于修好已损坏数据。记录受影响数据识别方法、修复方案、备份与回滚。
数据迁移、新约束、外部调用及生产更改依照原权限流程，技能不会授予执行权限。
核对混合版本、缓存旧值、任务在途状态及重试消费；需要额外工作时拆为明确后续任务。

## 5. 声明防复发范围

按以下格式结案：
“在版本 X、配置 Y、测试条件 Z 下，约束 G 阻止机制 M；测试 T 能检出其重新引入。
尚未覆盖条件 U；发布状态 D；线上观察信号 S；失败后的处置 R。”

监控只能发现，不应写成结构性防止。即使约束有效，绕过边界、迁移和新需求仍需单独验证。
不承诺任意未来修改均安全；门禁本身还需要被实际 CI 调用并受到变更保护。

## 6. 防止“越修越大”

本次修复需要的上下游协同一并完成，但无关命名、格式、架构优化单列。
若必须扩大范围，说明“现有边界为什么不能完整保护要求”，而非仅以代码整洁为理由。
按共同机制归类重复问题，保留每个具体症状与证据；不能只凭相似报错就认定同根因。
