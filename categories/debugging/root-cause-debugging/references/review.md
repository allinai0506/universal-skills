# 独立验收与反证

## 验收角色

审查者接收同一业务要求、固定的版本/补丁和原始证据，自行核对，不把实施 Agent 的结论作为前提。
不能使用子 Agent 时，用单独验收阶段完成同样工作，不虚构“独立 reviewer 已通过”。

## 四个必答问题

1. 根因解释如何被证据支持？哪些边仍是推测？“首个错误状态”是否只是首个被记录的错误？
2. 同一业务断言能否区分旧实现和新实现？旧实现失败是否真是目标 Bug，而非依赖或构建失败？
3. 防护位于哪个真实入口/事务/权限边界？其他写入者、调用者、重试或迁移是否绕过它？
4. 修复是否保留相邻合法行为，历史数据与发布状态是否交代？

## 对抗性检查

从影响范围选有意义的反例，不机械执行全清单：
空值与缺失、边界值、合法重复、过期状态、重复/乱序请求、失败重试、并发竞争、进程中断、旧版本读写。
重点验证“修复不成立”的条件，而不只是重跑实施者最容易通过的用例。
撤销关键修复或植入等价缺陷后，如果测试仍通过，应查清测试是否未经过目标机制。
不允许仅修改断言/fixture、跳过用例或把环境故障当成预期红测。

## 机械门禁与语义验收分开

`scripts/check_evidence.py` 能检查记录字段、引用关系、本地文件摘要、测试对照元数据和状态。
它不能证明：日志真实、命令真的执行过、断言符合业务、因果关系正确、覆盖充分或生产可发布。
日志完整性摘要不是可信来源签名；被同一提交修改的日志和 JSON 可以一起伪造。
需要强制执行时，在受保护 CI 中重跑真实测试，保留 CI 原生结果并设置必要检查。
不要让 PR 自行修改校验器与证据后就获得自动批准；校验规则变更需要独立审查。

## 结论状态

- 证据不足：列出能改变结论的具体缺口和取证办法。
- 临时缓解：说明限制、回滚及根因仍未关闭。
- 根因有证据支持：说明验证范围；不等于修复已完成。
- 修复已验证：注明版本、环境、测试与剩余风险；不等于已部署。
- 线上已观察：记录部署标识、观察窗口和信号；不声称未来零故障。

`close` 门禁中的 `fixed` 指本次代码修复的证据记录可进入人工关闭审核，不是产品线上健康证明。

## 衡量技能效果

用同一项目、相近风险的缺陷样本比较：同根因复发/已关闭缺陷、变更引发的回归/已发布变更、
达到经验证诊断所需时间、每次修复验证成本。分母、观察窗口和缺陷分类规则预先固定。
发布变更和后续复发未观察充分时不宣称有效性已证明。
报告长度、追问层数、PR 数量和覆盖率单项都不能充当根因正确性的证据。
