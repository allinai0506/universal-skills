# 溯源方法：从现象到可验证的致错机制

## 1. 先分清六个概念

| 概念 | 要回答的问题 | 不能混淆的情况 |
| --- | --- | --- |
| 现象 | 用户观察到什么错误？ | 异常抛出点不等于错误产生点 |
| 正确性依据 | 什么结果才对，来源在哪里？ | 新补写的测试不是业务规则的自动授权 |
| 触发条件 | 哪个输入、状态、配置或时序激活缺陷？ | 合法用户行为不是责任归因 |
| 致错机制 | 哪个具体行为造成预期与实际偏离？ | “架构差”“缺测试”不够具体 |
| 放大因素 | 什么让影响扩大或恢复更难？ | 无界重试、缓存和回退不一定是最初原因 |
| 逃逸原因 | 为什么约束、测试、监控未发现/阻断？ | 这是防复发输入，不可代替致错机制 |

缺陷可以潜伏，尚未导致可观察失败。一个失败也可由多个条件共同造成。
把“所有 Bug 都来自缺少不变量”作为万能结论，会遗漏需求错误、实现错误、环境差异和资源边界。
正确性可以是返回值、状态不变量、时序要求、隔离/权限要求，或明确的性能阈值。

## 2. 固定现场，不先堆补丁

记录运行版本与源码版本是否一致，配置/特性开关、依赖、租户或权限、相关数据、时钟/时区及输入摘要。
只收集与本问题有关的最小数据。客户文档、令牌、账号和连接串先脱敏；不把原始材料写进公共仓库。
在隔离副本构造最小复现；删掉无关输入时验证失败仍在，避免“最小化”时删掉触发条件。

## 3. 定位最早已知偏离，而不是宣称全局第一次

画一条与失败有关的路径，给每个边界标注：输入身份、输出身份、状态、事件顺序、证据位置。
从失败处向上追，也从可信入口向下核对。未观测的区间用“未知”表示，不补写成正常。

例：输入已记录正确 → 持久化结果未知 → 后续读取得到错误状态。
这里的结论是“错误发生在两处观测之间”，不是“已经证明持久化组件有错”。

并发或异步任务用 request/run/task/event/transaction 标识关联；时钟时间不能单独证明跨节点因果。
若存在先后关系、多个写入者或读写竞争，用因果图或事件偏序，不强造一条线性执行链。

## 4. 假设—预测—区分实验

| 假设 | 若成立应观察到什么 | 区分实验 | 结果/证据 | 结论 |
| --- | --- | --- | --- | --- |
| H1：具体机制 | 可证伪预测 | 控制一个关键条件 | 如实记录 | 支持/反对/未决 |

只有一个确定性失败断言且相关实现直接违反它时，无需虚构 H2/H3。
存在歧义时优先做能区分修复方向的实验，不反复运行同一无信息量命令。
代码阅读、时间相关和同一提交的多处变动都只能提供线索；用控制实验增加因果支持。

区分实验可包括：固定输入交换实现、注入失败点、控制调度、修复前后比较、恢复致错条件。
反证实验应保留同一业务预期。改输入、改断言、改环境的比较必须说明差异，不能冒充受控对照。
出现无法解释的反例时回到假设阶段，而不是增加特判直到个别样例通过。

## 5. 版本溯源

已有明确好版本、坏版本和可信判定脚本时，使用 git bisect 缩小引入区间。
在独立 worktree/副本操作，先检查工作区；不在用户未提交改动上切版本、reset 或强制清理。
记录 bisect 的 good/bad/skip 与构建条件；无法构建的版本不能默认标成有 Bug。
引入提交只是时间定位，仍要说明该变更如何导致失败；环境漂移或多个不连续回归会影响解释。
命令用法参见 sources.md 的 Git 官方文档，不猜测仓库测试命令。

## 6. 什么时候停止继续追问

在明确边界内，机制能解释目标失败和正常对照；已有可复核实验支持；修改边界与风险明确。
不强迫把每个 bug 都追到组织文化，也不要求先证明整个系统无缺陷。
缺少的证据会改变修复方向时继续取证；证据不可取得时交付诊断缺口，不声称根因已证实。
线上事故可以先经授权止血，并保持“临时缓解，根因未关闭”的状态。
