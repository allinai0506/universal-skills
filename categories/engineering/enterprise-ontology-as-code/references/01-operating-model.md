# 01 Operating Model：如何真正落地

## 原则

不要建立一个“本体论项目”。把 Ontology 当作业务代码的一部分。

每个业务需求都问 8 个问题：

1. 新增/修改了哪个业务对象？
2. 关系是否变化？
3. 状态机是否变化？
4. 决策规则是否变化？
5. 可执行动作是否变化？
6. 权限是否变化？
7. 外部系统映射是否变化？
8. 哪些 Agent / Workflow 的 Projection 需要变化？

如果答案全部是否，则普通业务 PR 不需要修改 Ontology。

如果任一答案为是，则 PR 必须带 Ontology Diff。

## 工程组织

推荐把 `ontology/` 放在仓库根目录，与 `src/`、`tests/` 同级。

不要先做 Ontology 管理后台。第一阶段文件优先，因为：

- Git 天生提供版本、Diff、Review、Rollback。
- Coding Agent 可以直接读取和修改。
- CI 可以验证。
- 不引入新的服务和数据库。

等 Ontology 稳定并且多人协作频繁后，再做 UI 管理工具。

## 每次只做一个 Vertical Slice

例如电子会计档案的第一片：

`记账凭证 -> 原始凭证 -> 匹配 -> 完整性 -> 归档`

不要同时建：组织、用户、合同、预算、发票、付款、税务、供应商全部模型。

## 何时升级一个概念到 Ontology

至少满足一项：

- 多个模块/Agent 会共享。
- 有稳定业务含义，不是纯技术结构。
- 参与业务决策。
- 参与状态变化。
- 参与权限判断。
- 需要长期避免语义漂移。

否则留在局部代码即可。
